# LongMemEval：论文与代码精读

本篇研究如何评测助理在长时间互动中记住信息，以及如何拆分和改进记忆流水线。它提供基准和设计实验，没有提出需要重新训练的大型神经记忆网络。按本次要求，只制作中文解释和小 demo，暂不翻译全文。

## 3. 五种能力为什么会有七种题型

信息提取 IE 包含 user、assistant 和 preference 三种题。用户说过什么、助理推荐过什么、多个表达暗含什么偏好，难点不同。MR 是跨会话汇总或比较；KU 关注个人状态变化后哪个是当前信息；TR 关注相对时间、日期以及事件间隔。ABS 要识别历史中根本不存在的信息，不能因为检索出了“看起来相关”的段落就编答。

原文件 question_type 的六类总数为：user 70、assistant 56、preference 30、multi-session 133、temporal-reasoning 133、knowledge-update 78，共500。30道 ABS 保留其原始 question_type，通过 question_id 中 _abs 标识，不能在六类总数外再加30。检索评测跳过 ABS，因为没有真实答案位置；回答评测必须保留它们。

比如先说住北京，后说搬到杭州：KU 应回答杭州，却可能仍需保留“以前住北京”供历史问题使用。比如五月问“上个月去哪里”，应推断四月发生的事件，不能仅找四月发送的消息。用户六月补述“四月去了南京”，事件日期四月、会话日期六月，过滤对象应区分。

## 4. 数据如何构造，能评测什么

论文定义164种用户属性，涉及生活方式、物品、人生事件、情境与人口属性。背景由模型生成，问题与证据陈述经过人工创建和编辑；两个模型模拟用户与助理交互，再经人工修正证据、措辞和位置。附录说约70%的证据会话有人工作业。填充历史来自其他不冲突属性的自聊以及 ShareGPT、UltraChat，按约束混合并附上时间。

因此每个问题有自己的用户历史，不应把500题的所有 session 无差别塞进同一用户记忆库。也不能把 gold answer 或 has_answer 标签送进检索器。问句、历史、日期是系统输入；答案和答案位置是测量标签。

S 约115k token；M 500会话、约150万 token。这些 token 数依赖论文使用的 tokenizer，不能用文件字节或本机 split 空格计数替代。Oracle 只保留证据会话，帮助隔离阅读能力；若用 Oracle 做检索，会大幅降低难度，不能声称复现完整 S/M 检索。

图2流程中背景、题目、证据与模拟会话是数据构造过程，不是运行每次检索时的模型计算。图1的箭头从若干历史片段走到问题和目标答案，没有表示 gold 信息可以给系统。合成历史可扩展但不等于自然长期使用日志：人为设定的属性冲突、对抗输入、删除与用户权限变化仍需另测。

## 5. 数学与变量形状

### 5.1 历史、索引和查询【必须会】

§3.1 的评测实例为

$$ (S,q,t_q,a),\qquad S=[(t_1,S_1),\ldots,(t_N,S_N)],\quad t_q>t_N. $$

S 是长度 N 的列表；每个 S_i 是 list[dict]，字典里有 role 和 content 两个主要字符串；t_i、t_q 是日期时间；q 是问句；a 是短答案或开放问题的 rubric。它们不是张量。一个 round 通常是用户一条消息和紧随其后的助理回复，session 则有多个 round。

§4/附录C把记忆写作

$$ D=[(k_1,v_1),\ldots,(k_m,v_m)],\quad
D_i=I_{online}(S_i,D_{i-1}),\quad q'=Q(q),\quad
D'=\operatorname{TopK}(\mathcal{S}(q',D)),\quad \hat a=R(M,D'). $$

这里用 $\mathcal{S}$ 区别历史 S 与论文中同样叫 S 的 salience 函数。I 建索引，Q 变换查询，评分函数排序，R 用阅读模型 M 回答；$\hat a$ 是系统输出。上式是对附录文字定义的整理，不是论文一个带编号的新训练损失。在线 I 可以修改或删除旧条目，而本地 demo 是从每题已有完整历史构造静态索引，未模拟逐会话到达。

离散 key 是字符串、value 是会话/round；稠密 key 可为 $E(k_i)\in\mathbb R^d$。m 个键堆叠是 $[m,d]$，query 是 $[1,d]$，点积产生 $[1,m]$ 分数，再取 K 个位置索引 $[K]$。Stella 实现 d=1024，模型原生输出需通过额外 Linear 层再归一化；本 demo 的 BM25 不生成这类 embedding，也没有梯度或 optimizer。

数字例：D 有3个 round，评分为[0.4,0.9,0.2]，K=2返回位置[1,0]。阅读前按日期重新排序，不会变成“再按相似度选一次”。key 扩展可以变长而 value 保持原始 round。二者恰好一样只是 K=V 的一种设计。

### 5.2 Key 扩展与粒度【必须会】

推荐 key 可写为

$$ k_i=\operatorname{concat}(\operatorname{Facts}(v_i),\operatorname{UserText}(v_i)). $$

它把提取事实放在原用户文本前方，帮助匹配的同时保留细节。两输入和输出均为 string；事实生成前通常为 list[str]。比如原文“这个镜头适配我的 A7R IV 吗”，扩展事实“用户使用 Sony A7R IV”，合并后 key 保留两句。直接用摘要替换 value 则会删去读者可见细节，二者不可混淆。

原 resolve_expansion 中 merge 在匹配 ID 处创建拼接 key；replace 替换 key；separate 加入另一条同 value ID 的键。split-merge 可以生成多个同 ID 键。原函数接收三个平行 list：语料、ID、时间，返回三列表；separate 会用 += 原位修改，merge/replace 创建新列表。实际小探针调用 merge 后得到“user likes Sony original detail”，验证的是拼接，不是真实模型能正确提取事实。没有运行 NLTK sent_tokenize 的 split-summary 分支。

原 process_item_flat_index(session,granularity,sess_id,timestamp) 返回 list[str] 文本、list[str] ID、list[str] 时间。session 粒度将所有用户消息拼接为一个 key；turn 粒度每个用户消息一个 key。助理原文不进入这个检索 key，但原 generation 的 flat-turn 会取中选用户消息和紧随其后的回复构成 round value。因此源码选项 turn 在检索和阅读阶段含义略有不同。

### 5.3 检索指标【必须会】

设 G 为正例 ID 集合，H_K 为前 K 项返回的 ID 集合，原评分函数计算

$$ R_{any}@K=\mathbf1[G\cap H_K\ne\varnothing],\qquad
R_{all}@K=\mathbf1[G\subseteq H_K]. $$

每题分数是0/1，再跨题求平均。这与上一篇 LoCoMo 的每题“找到证据比例”不同。G={a,b}，H_3={a,c,d} 时 any=1、all=0；平均文档 recall 则是1/2，三个数各有不同含义。all 常适用于必须聚合多段证据的问题。

原 dcg 使用另一种折扣约定：

$$ DCG@K=r_1+\sum_{j=2}^{K}\frac{r_j}{\log_2 j},\qquad NDCG@K=\frac{DCG@K}{IDCG@K}. $$

r_j 为第j位置是否为正例，IDCG 把正例排在前面得到理想值；IDCG=0时原函数返回0。注意第一和第二名权重都是1，不能擅自套用 $\log_2(j+1)$ 后还称同一指标。数字例：相关性[0,1,0]、唯一正例时 DCG=1、IDCG=1、NDCG=1，尽管 top1 没找到答案。本次原函数实测如此。

evaluate_retrieval(rankings,correct_docs,corpus_ids,k=10) 是函数，输入分别为长度m的位置排序 list[int]、正例 list[str]、语料ID list[str]，返回三个 float：any、all、NDCG，不修改输入。ndcg 将 binary relevance 排列成 NumPy [m] 数组；dcg 用 asfarray。本机 NumPy1.21.6兼容；不能直接拿不再提供这个 API 的环境假定通过。

原函数对 G=空集合产生 any=0、all=1、NDCG=0，这是 Python all([]) 为 True 的逻辑结果。原检索程序依据 ID 中 answer 字样产生 gold，索引函数又会把无用户侧 has_answer 的会话 ID 改为 noans。assistant 类型可能因此没有正例，即使原数据 answer_session_ids 并非空。本 demo 发现9题如此，保留错误口径并单列诊断，未修改作者仓库。

原评分函数的核心代码如下（原函数体中的连续语句）：

~~~python
recalled_docs = set(corpus_ids[idx] for idx in rankings[:k])
recall_any = float(any(doc in recalled_docs for doc in correct_docs))
recall_all = float(all(doc in recalled_docs for doc in correct_docs))
ndcg_score = ndcg(rankings, correct_docs, corpus_ids, k)
return recall_any, recall_all, ndcg_score
~~~

第一行用位置idx找ID，把前k个ID去重成set[str]；生成式逐个产生ID，不创建额外文本索引。第二行any检查是否至少一个正例命中；第三行all检查所有正例是否命中；float把True/False转为1.0/0.0。第四行转交原ndcg函数计排序分；第五行返回tuple[float,float,float]。这段不调用模型、不读取gold答案字符串、不写数据库，位于排名完成之后。正例为空时any/all的不同逻辑正是本次诊断来源。掌握等级：必须会。

### 5.4 BM25【建议会】

源码的低成本分支使用 rank_bm25.BM25Okapi。分词就是 doc.split(" ") 和 query.split(" ")，保留大小写及标点；本 demo 没偷偷换为更强的 stemmer。

$$ score(q,d)=\sum_{w\in q}IDF(w)\frac{f(w,d)(k_1+1)}{f(w,d)+k_1(1-b+b|d|/avgdl)}. $$

f 是词频整数；|d|、avgdl 是文档/平均词数；k1=1.5、b=.75是0.2.2默认值。IDF 使用该库的 log 差值与负值修正，不能假设每个 BM25 实现相同。单词 IDF=1、平均长度文档、词频2时，该词贡献为 $2\times2.5/(2+1.5)=1.4286$。scores 是 NumPy [m] 浮点数组，原 np.argsort(scores)[::-1] 输出 [m] 位置索引；tie 顺序继承 NumPy 排序行为。

### 5.5 时间范围与稳定重排【必须会】

论文按事件日期而非仅会话时间缩小检索范围。原代码对推断区间[begin,end]两侧各扩2天，然后执行稳定分组：

$$ H'=\operatorname{stable}(H;\;date(event)\in[begin-2,end+2])\;\Vert\;
\operatorname{stable}(H;\;date(event)\notin[begin-2,end+2]). $$

$\Vert$ 是列表拼接。它没有删去范围外候选，而是把它们移到队尾，同组保留原相似度顺序。最终 topK 会排除很多候选，因而看起来像过滤。事件日期为 YYYY/MM/DD 可进行字典序比较；格式不一致或月日未补零会破坏含义。

infer_time_range(query,query_date) 构造1条 system +10组示例问答+1条 query，共22条消息，要求模型给 start/end 或 N/A。解析失败返回{}；另有 start 是 query_date 子串就返回{}的 hack，这会忽略一些发生在当天的合法区间。日期解析和提示函数执行了原代码，但三次返回由本地 Provider 指定：四月区间、N/A、当天区间。不能据此评估真实 LLM 日期推断正确率。

小例原排序[旧填充,答案事件,未来填充]，正确四月范围把答案升到第一；错误五月范围把答案推至最后。记录总候选数始终3。两天容错不是事件日期精确性保证，也可能引入额外干扰。

|---|---|---|

### 9.3 阅读提示与judge：原代码中的修改顺序
