# Zep：论文与代码精读

这篇论文关注动态 Agent 记忆：不仅要检索“用户住哪里”，还要分清“当时住哪里”和“系统当时知道什么”。核心是 Graphiti 的时间知识图谱、增量构建和多路检索。建议先理解两条时间轴，再读失效边的源码，最后审视实验中的上下文压缩与准确率。

## 2. 三层图：原消息、事实和概括不能互相代替

【必须会】论文 §2 定义未编号图 $G=(N,E,\varphi)$，$N$ 是节点集合，$E$ 是边集合，$\varphi:E\to N\times N$ 把一条边映射为源、目标节点。它是离散数据结构，不是神经网络权重张量。正文还使用 $\varphi^*$ 表示由节点对对应边的记法，不能理解为矩阵转置或梯度。

Episode 子图 $G_e$ 保存 message/text/JSON 原始输入，消息包含发言人及 reference time；episode 边连到提取的实体。Semantic 子图 $G_s$ 的实体节点表示人、地点、组织等，实体间的语义边携带事实。Community 子图 $G_c$ 保存关联实体群组的概括，社区边连到成员实体。

例子：episode 原文“我二月搬到杭州了”；实体 Alice、Hangzhou；事实 Alice lives in Hangzhou；社区摘要可以概括 Alice 的生活与旅行。摘要便于全局检索，不能替代原消息细节。论文所谓 non-lossy 主要来自原 episode 的保留与事实来源链接，不是保证抽取没有错误或所有记忆永远进入回答上下文。论文明确 episode↔fact 的引用/回溯能力没有在本次实验直接检验。

实体和事实不同：Alice 是节点，“Alice住杭州”是边事实；发言人自动作为实体有助于代词消歧，但不会自然解决所有同名问题。一个复杂多实体事实可通过多个实体对的边表达，论文称其具有 hyper-edge 效果；不要因此假设底层数据库直接用一个超边对象连接任意个节点。

## 3. 构建流程：先明确身份，再建立关系

§2.2：抽取当前消息的实体时还给最近 n=4 条消息，帮助理解指代；随后进行反思以改善覆盖、提取实体摘要；实体名称嵌入到1024维，再结合全文搜索召回旧节点，由 LLM 判定是否同一实体，并更新名称与摘要。1024 是论文使用 embedding 的维度，不是所有 Graphiti 后端必须遵守的常量。

数据形状：当前消息为 str；近期消息为 list[Episode]；候选实体为 list[EntityNode]；单实体 embedding 为浮点 [1024]，候选矩阵可理解为 [K,1024]，K 随召回变化。字段 name、summary、uuid 为字符串；日期为有时区 datetime。这是 LLM 调用和图数据库对象流，没有本论文定义的 attention head、训练损失或反向传播流程。

事实提取后也嵌入并去重。论文说去重相关边限制在相同实体对，以避免不同人的相似事实被合并。对矛盾检测则需要相关旧关系候选，例如 Alice→Beijing 和 Alice→Hangzhou 的居住事实目标不同，不应把所有候选阶段都笼统说成“只比较完全相同实体对”。归并使用模型判断；相似召回只是生成比较候选。

最终写库使用预先定义的 Cypher，而非让 LLM 任意编写数据库语句。这样使 schema 更稳定，但无法保证被写入的事实内容正确。实际应用还需考虑消息注入、错误抽取、并发及来源权限，本次不声称完成这些验证。

### 3.1 构建主入口的函数语义

Graphiti.add_episode 从 graphiti.py 第253行起，是 async 方法：输入 name、episode_body、source_description、reference_time，另有 source 类型、group_id、uuid、update_communities；返回 AddEpisodeResults（以实际代码为准，旧 docstring 的 None 不足以证明返回类型）。owner 是 Graphiti，更新图中的 episode、实体与边。

执行链：retrieve_episodes → 构造 EpisodicNode → extract_nodes → embeddings → 节点解析 → extract_edges → 去重/时间抽取/矛盾解析 → 写入节点与边 → 可选社区更新。原入口允许 store_raw_episode_content=False 时清空 episode.content，所以 non-lossy 原文保留也依赖配置。created_at 来自系统 utc_now，episode.valid_at 来自传入 reference_time；这已经体现系统接收与消息时间的区别。

async def 定义协程，调用后需要 await 执行完成。semaphore_gather 允许部分子任务并行，但文档推荐 episode 顺序加入并等待，避免多个写入彼此看不到上下文。group_id 是分区条件，不等于完整权限管理证明。demo 没有运行完整 add_episode 或 Neo4j。

## 4. 双时间：事实变化与系统认知变化

【必须会】论文 §2.1/2.2.3 区分事实时间轴 $T$ 与事务/接收时间轴 $T'$。一条语义边记录四个时间：

| 论文符号 | 源码字段 | 含义 |
|---|---|---|
| $t_{valid}\in T$ | valid_at | 事实从何时成立 |
| $t_{invalid}\in T$ | invalid_at | 事实从何时不再成立 |
| $t'_{created}\in T'$ | created_at | 系统何时建立这条记录 |
| $t'_{expired}\in T'$ | expired_at | 系统何时把它判为失效 |

reference timestamp $t_{ref}$ 是输入消息的参考时间，可用于“上周”“两周前”等相对日期解析。它不必等于系统今天运行的时刻，也不一定等于事实有效期的起点。例如3月收到“二月搬家”的消息，消息时间、事实时间、接收时间可全部不同。

以下为本 demo 的查询约定，并非论文编号方程：给事实时间 $q$，半开区间可见性为

$$\mathrm{active}(e,q)=(t_{valid}(e)\le q)\land(q<t_{invalid}(e)).$$

不存在开始或结束字段时，demo 分别按无限过去/未来处理；真实业务应明确 unknown 与无界的区别。若北京区间为 [1月1日,2月1日)，杭州为 [2月1日,3月1日)，3月1日查询应只看到上海，不能让边界两座城市同时生效。比较的是 datetime，不是字符串词序或数字 token 位置。

### 4.1 乱序事件示例

系统1月2日收到“1月1日起住北京”；3月2日收到“3月1日起住上海”；4月1日才收到“2月1日起住杭州”。按照已知事实的最终解释，北京应在2月1日结束，杭州在3月1日结束，上海仍为当前。

“4月1日最后写入杭州”不应直接推导“现在住杭州”。同时，对“截至3月2日系统如何回答2月15日住哪里”，当时还没有杭州事实，答案可能是北京；收到补充之后对同一个事实日期答杭州。两条时间轴解决的是两类查询，而不是两个同义 timestamp。

要严格回答系统过去的认知状态，单条边当前四字段未必够。源码会把旧边 invalid_at 从3月1日改到2月1日，同时保留已有 expired_at，旧边先前版本的 invalid_at 值不会自动保留下来。demo 因此由本地宿主保存每次完整快照，模拟事务时刻的历史视图；这是额外教学存储，不是宣称 Graphiti 四字段自带完备的 SQL 双时间版本查询。

### 4.2 resolve_extracted_edge：原代码的时间决策

[edge_operations.py](代码/graphiti-historical/graphiti_core/utils/maintenance/edge_operations.py) 第260行起。输入 LLM client、新边、相关边、现存候选、当前 episode 与以前 episodes；输出 tuple[EntityEdge,list[EntityEdge]]，分别是解析后边与被失效旧边。它会就地改变边字段，不是纯函数。

三个任务并行：dedupe_extracted_edge 判重复；extract_edge_dates 解析有效期；get_edge_contradictions 选矛盾候选。之后填有效期，并检查新边本身是否已经过时：如果矛盾候选有更晚的 valid_at，设置新边 invalid_at 为那个较晚起点，expired_at 为当前接收时刻。再让 resolve_edge_contradictions 处理旧边。

关键原代码摘录：

~~~python
if candidate.valid_at > resolved_edge.valid_at:
    resolved_edge.invalid_at = candidate.valid_at
    resolved_edge.expired_at = now
    break
~~~

候选先按有效期排序；选择后面的边界，让晚收到的旧事件止于已知后续事件。candidate 是 EntityEdge 对象，点号读取字段；有效期还检查 tzinfo，避免混用无时区和有时区日期。not/None 判断是在选择缺失值逻辑，不是神经 gating。

### 4.3 resolve_edge_contradictions：只让重叠且更早的事实结束

第230行起，输入 resolved_edge 与候选 list[EntityEdge]，返回实际失效列表并修改候选对象。先跳过不重叠区间：旧边已在新边开始前结束，或新边在旧边开始前已结束；随后只在 old.valid_at < new.valid_at 时，把 old.invalid_at 设为 new.valid_at。expired_at 如果已存在就保留，否则 utc_now。

~~~python
edge.invalid_at = resolved_edge.valid_at
edge.expired_at = edge.expired_at if edge.expired_at is not None else utc_now()
~~~

三元表达式决定是否第一次记录失效时间。list 中保存的是对象引用，所以改 edge 会影响宿主保存的同一对象。demo 的北京边起初被上海截断，后来又被杭州改短，但 expired_at 保留原第一次失效时刻。

重要边界：两个矛盾事实 valid_at 完全相同，严格小于条件不会使旧边失效。本实验观察到同起点矛盾未解决，并把它作为限制记录；断言“此行为出现”通过，不等于该冲突正确解决。日期为空或抽取失败也不是默认获得一致性。论文以新信息优先描述系统行为，而这份锁定实现仍要结合具体区间、候选和分支理解。

### 4.4 时间抽取与矛盾判别不是确定性事实验证

[temporal_operations.py](代码/graphiti-historical/graphiti_core/utils/maintenance/temporal_operations.py) 中 extract_edge_dates 给模型 fact、当前/旧 episode 和 reference_timestamp，读取 valid_at/invalid_at，处理 Z 时区并 fromisoformat。无效字符串捕获 ValueError 后返回 None 并写 warning。ensure_utc 将无时区 datetime 假定 UTC，或把有偏移日期转 UTC；这不会帮用户猜出实际本地时区。

get_edge_contradictions 用 UUID 建 map，仅接受来自现存候选的 ID，并按模型响应更新候选 fact。这个 ID 检查减少未知对象引用，但不能证明模型选中的矛盾正确。demo 在这部分注入可控响应，实际自然语言判断仍未验证。

## 5. 社区与读取：多路召回、排序、构造上下文

【建议会】社区初建采用 label propagation，而不是直接复用 GraphRAG 的 Leiden。增量新节点看邻居所处社区，选择最多邻居支持的社区并更新摘要；这只是动态近似，会逐渐偏离全量重算，需要周期刷新。邻居社区 A,A,B 时选择 A；频率统计是图操作，摘要生成才调用 LLM。社区摘要为 map-reduce 式概括，名称含关键词并嵌入供搜索；不是每次查询都遍历所有社区回答。

§3 使用未编号组合公式：

$$f(\alpha)=\chi(\rho(\phi(\alpha)))=\beta.$$

$\alpha,\beta\in S$ 是输入查询、输出上下文字符串；这里的搜索函数 $\phi$ 与 §2 incidence $\varphi$ 角色不同。$\phi$ 返回事实边、实体、社区的三组候选 list；$\rho$ 是重排序，改变顺序/选择；$\chi$ 将边的 fact/valid_at/invalid_at、实体 name/summary、社区 summary 格式化成文本。接口输入为 str，输出仍为 str；候选条数不固定，可抽象为 [K_edge]、[K_entity]、[K_community] 对象列表。它并不是直接输出最终问答答案，答案需要另一个回答模型。

Search 三路：cosine 查语义相似，BM25 查词面，BFS 查图邻域关系。BFS 的“近”是图路径长度，不等于时间最近；也不保证所有近邻相关。BFS 可用最近 episode 中提及实体作种子，扩展若干跳。cosine 和全文字段分别依事实、实体名、社区名而定，不要混称搜索全部原始消息。

### 5.1 RRF 数值例子与代码

【建议会】[search_utils.py](代码/graphiti-historical/graphiti_core/search/search_utils.py) 第652行的 rrf 输入 list[list[str]]，rank_const 默认1，输出融合 UUID 列表，不改变图存储。核心：

~~~python
for result in results:
    for i, uuid in enumerate(result):
        scores[uuid] += 1 / (i + rank_const)
~~~

对应教学公式（非论文编号式）：

$$\mathrm{score}(x)=\sum_{l:x\in L_l}\frac{1}{i_l(x)+c}.$$

索引 $i_l$ 从0开始，$c=1$。defaultdict(float) 给新 ID 初始化0；enumerate 同时返回索引/ID；排序按累积得分递减。这不是把 cosine 和 BM25 原始分数直接相加。

demo 三个列表 [北京,上海]、[杭州,上海]、[巴黎,上海]，上海在每路第2位，各得1/2，合计1.5；其他项仅各路第一位得1，最终上海第一。其余同分按稳定的插入顺序处理。这个例子说明多路一致性可超过单路第一，不证明真实召回质量。

其他排序包括 MMR、episode mentions、节点到中心距离、cross-encoder。cross-encoder 为查询和候选共同打分，通常增加模型成本。本历史版本 maximal_marginal_relevance 对候选比较所有候选（包含自身）的相似度，并最终 list(set(...))，不能把它无条件说成标准逐步选取且严格保序的 greedy MMR。本文不依赖这个函数运行结果，也没有进行质量排名实验。

## 6. 实验与结论边界

### 6.1 设置与范围

建图用 gpt-4o-mini-2024-07-18；回答用该 mini 与 gpt-4o-2024-11-20，DMR另用 gpt-4-turbo-2024-04-09；embedding/reranking 使用论文称 BGE-m3 的 BAAI 模型体系。不是本机安装后端的实测配置。LongMemEval_s 平均115k token；本论文通过 Zep APIs 入库和检索，再给回答器上下文，judge 采用 GPT-4o 与问题类型专用提示。

§4 总体设置提取20个相关事实/实体，§4.2 DMR又写 top10 nodes/edges。应保留这处任务配置差别/说明不一致，不能为所有实验强行填同一个 k。论文未在这里公开所有建图成本、完整 schema/服务配置及每条原始响应。3种图的能力不等于都被独立消融验证，特别是 episode 来源回溯与社区能力没有由这些表单独证明。

### 6.2 表1：DMR 已接近全上下文天花板

DMR为500组对话，每组5个会话、每会话最多12消息，一组约60消息和一个问答。分数越高越好；MemGPT/recursive summarization 引用先前论文结果，其余为作者基线/实验。

| 回答模型 | Full conversation | Zep | Zep绝对增益 |
|---|---:|---:|---:|
| gpt-4-turbo | 94.4% | 94.8% | 0.4个百分点 |
| gpt-4o-mini | 98.0% | 98.2% | 0.2个百分点 |

同 turbo 模型 MemGPT 为93.4%，Zep高1.4个百分点。不要把摘要的94.8 vs93.4写成全面证明架构胜出：全历史94.4已经很接近；mini 的差0.2个百分点在500样本下对应约1题，且未报告本表置信区间。作者指出问题短、只测单事实、部分措辞含糊，难代表长期复杂记忆。未成功复现 mini MemGPT 不是它在 mini 上分数为0。

### 6.3 表2：LongMemEval_s 的质量与上下文压缩

[表2/表3原图](图片/page-7.png)。

| 回答模型 | 方式 | Score | Latency | Latency IQR | 平均上下文 |
|---|---|---:|---:|---:|---:|
| gpt-4o-mini | Full context | 55.4% | 31.3s | 8.76s | 115k |
| gpt-4o-mini | Zep | 63.8% | 3.20s | 1.31s | 1.6k |
| gpt-4o | Full context | 60.2% | 28.9s | 6.01s | 115k |
| gpt-4o | Zep | 71.2% | 2.58s | 0.684s | 1.6k |

### 7.2 三任务汇合：原代码与连续变量流

【必须会】edge_operations.py 的 resolve_extracted_edge 原节选，处于候选检索之后、数据库写入之前：

~~~python
resolved_edge, (valid_at, invalid_at), invalidation_candidates = await semaphore_gather(
    dedupe_extracted_edge(llm_client, extracted_edge, related_edges),
    extract_edge_dates(llm_client, extracted_edge, current_episode, previous_episodes),

resolved_edge.invalid_at = invalid_at if invalid_at else resolved_edge.invalid_at
~~~

一句话：并行询问重复/日期/矛盾，再更新解析边的时间。API/语法：async def定义协程，调用产生awaitable，await等完成；本地semaphore_gather(*tasks)的星号收集位置参数为tuple，再通过asyncio.gather(*tasks)展开。返回按传入顺序，不按完成速度。左侧嵌套解包要求三个结果，中间为两个日期。a if condition else b是条件表达式，None是假值，所以空响应保留旧字段。对象.字段赋值改变原引用，可能改变外部edges列表中的旧边。

| extracted_edge，抽取边 | 当前episode的事实 | EntityEdge标量，fact:str | 三任务共读 |

### 7.3 日期与候选原代码：解析和修改在哪里发生

【必须会】temporal_operations.py 日期片段，将模型ISO字符串变成UTC datetime：

~~~python
existing_edge_map = {edge.uuid: edge for edge in existing_edges}
~~~

### 7.4 时间谓词、教学流程与运行证据

【必须会】§4半开查询是教学规则，补全符号和步骤：

$$
\operatorname{active}(e,q)=
(s_e=\mathrm{None}\ \lor\ s_e\le q)
\land
(u_e=\mathrm{None}\ \lor\ q<u_e).
$$

e一条边，q待查事实时刻，s_e=e.valid_at/u_e=e.invalid_at，都是带时区datetime标量或缺失；active为bool。先检查开始，再检查结束，最后与用户条件相与。None界宽松视为无限延伸只是宿主约定，不证明事实永恒。杭州s=2月1日、u=3月1日，q=2月15日为True，q=3月1日结束条件False；映射本地active_at，原服务过滤未运行。

“系统在事务时刻r相信什么”不能只用created_at≤r<expired_at恢复后来已被修改的invalid_at。r是系统认知时刻，q是事实时刻。本地先选r之前保存的状态快照，再对其active(e,q)查询。3月2日快照中2月15日为北京，4月1日修正后为杭州；这由额外快照实现，原完整事务版本查询未找到已运行证据。四字段不自动保留所有旧字段版本。

【必须会】§3未编号公式 $f(\alpha)=\chi(\rho(\phi(\alpha)))=\beta$：alpha查询str；phi多路召回边/实体/社区三个可变长度候选集合；rho排序筛选；chi构造文本；beta记忆上下文str，尚不是答案。步骤召回→排序→文本化。教学例alpha“现在住哪里”，召回北京/杭州/上海，再按查询时刻筛失效事实，格式化“当前：上海”；未执行原chi或证明原ranker必然这样筛。Graphiti.search返回边仅覆盖一部分，完整服务Constructor映射未确认，cosine相似不等于时间有效。
