# MemGPT：论文与代码精读

本地论文为 arXiv:2310.08560v2（2024-02-12，13 页）。作者 Charles Packer、Sarah Wooders、Kevin Lin、Vivian Fang、Shishir G. Patil、Ion Stoica、Joseph E. Gonzalez，单位 UC Berkeley。原文见[原论文](原论文.pdf)，下载版本和 SHA256 见[元数据](资料/论文元数据.json)。本文解释机制、代码和实验，不制作全文翻译。

最重要的区别是：MemGPT 把长期信息存到模型外部，再通过工具把当前需要的信息放回上下文。它不通过测试时梯度把新事实写进模型权重。有限上下文始终有限，“虚拟上下文”来自选择性读写和反复调用。

## 3. 三种主上下文与两种外部存储【必须会】

| 区域 | 是否在当前模型输入中 | 谁写入 | 作用 |
|---|---|---|---|
| System instructions | 是 | 系统配置；模型只读 | 工具、记忆层级、控制规则 |
| Working context | 是 | 模型调用编辑函数 | 常用用户事实、persona、偏好 |
| FIFO queue | 是 | queue manager | 当前对话、工具调用和回复、系统事件 |
| Recall storage | 否 | manager 保存历史 | 找回以前的原始消息 |
| Archival storage | 否 | 导入或工具写入 | 更大文档、任意长期文本 |

Working context 与历史代码 CoreMemory 对应。CoreMemory 有 persona 与 human 两段字符串；它最终也渲染在 system message 里，但不能因此将可编辑的事实块与只读的系统规则混为一谈。

Recall 是消息历史；archival 是更一般的知识/文档存储。保留一条原始消息不等于自动提取了结构化事实，也不保证以后检索能命中。检索得到的信息必须进入主上下文后，模型才看得到。模型没有凭空读取整个数据库的能力。

一个完整输入可示意为：

$$P_t=S\oplus W_t\oplus H_t,\qquad |P_t|+R\le B.$$

S 是系统规则，W_t 是 working context，H_t 是队列和摘要，⊕ 是文本/消息的拼接；B 是模型窗口，R 是为输出和其他开销预留的空间。这里的 |·| 应按真实模型 tokenizer 计数，不是 Python 字符数。

示例预算：B=8,000 tokens，系统 1,000、事实 500、输出预留 500，则队列不能直接占满 8,000，剩余约 6,000。各数字是解释用的假设，不是论文统一配置。JSON 包装、工具 schema 和模型特有 message overhead 也会消耗 token。

本 demo 明确使用 1,200 字符预算，只展示有界上下文机制。字符数不能换称为 token，尤其中文、UUID 与 JSON 的 tokenizer 行为不同。

## 4. Queue manager：写历史、预警、换出【必须会】

消息进入系统时先记录到 recall，再加入当前队列。容量紧张时可以预警，让模型用工具保留重要内容；达到刷新条件时，旧队列消息被移出当前上下文，并用旧摘要与新移出内容生成递归摘要。原始消息仍在 recall 中。

移出 ≠ 删除数据库；摘要 ≠ 无损压缩。摘要忘记的细节可以通过原始历史检索恢复，但检索没命中或模型没调用工具，仍会失败。

论文 §2.2 用 70% 的 warning、100% 的 flush 和移出约 50% 内容作为例子。锁定代码 constants.py 的 MESSAGE_SUMMARY_WARNING_FRAC 实际是 0.75，summarization 截断比例也是 0.75。这些不是相同层面的固定常数。Agent.step 在模型返回 usage 后检查预警标志；遇到上下文溢出错误则调用 summarize_messages_inplace 再尝试。不能将论文示例当成这个 commit 的逐行行为。

工具调用与返回应配对保留，避免只留下没有上下文的 tool reply。本 demo 将一次工具名、参数和回复存成一个 atomic block；换出整块，不从中间切开。摘要只记录“已移出多少块”，故意不概括事实；这是用于隔离 recall 检索效果的替代，不是执行论文的 LLM 递归摘要。

## 5. Function executor 与控制循环【必须会】

图 3 的路线是：事件 → queue manager → 主上下文 → LLM → 工具调用描述 → executor → 存储读写 → 工具结果进入队列 → 再次推理或 yield。事件既可以是用户消息，也可以是系统预警等。

LLM 生成工具名和参数，不直接执行任意 Python。代码验证函数存在、解析 JSON、取出 request_heartbeat，再将剩余参数传给绑定函数。运行错误被包装为工具反馈，放回上下文。反馈改变的是后续推理输入，不代表模型权重在此被训练。

request_heartbeat=true 表示当前工具完成后请求马上继续一轮推理，以便继续翻页或追踪下一个 key；yield 表示暂时把控制权交回外部事件。它与定时 heartbeat 不是同一个用途。历史 main.py 的 process_agent_step 还优先处理 token_warning，其次 function_failed，再处理 heartbeat_request。因此一个错误即使未主动请求 heartbeat，也可能触发恢复轮次。

例：模型调用 core_memory_append 写入过长 human 字段 → CoreMemory 抛出容量错误 → executor 返回错误 → 下一轮可将长内容放到 archive 或缩短 core。只有工具数据真的被修改，才算记忆发生了变化，不能以自然语言“我记住了”作为保存证据。

本地 OfflineHost 重现“调用→结果→上下文”这条协议路线，但控制决策由 Python 脚本提供，没有让 LLM 自己生成请求，也没有执行原 Agent._handle_ai_response 的完整 JSON parser。max_calls=1 的对照模拟不允许继续的工具预算，不能声称它是对官方 heartbeat runtime 的完整消融。

## 6. 分页与多跳查询【必须会】

锁定代码中的默认 page size 为 5，page 从 0 起。页起始位置为：

$$\operatorname{start}=p\,s,\qquad\operatorname{last\_page}=\lceil N/s\rceil-1.$$

p 是页索引，s 是每页数量，N 是检索结果总量。N=12、s=5 时，页 0 返回索引 0—4，页 1 返回 5—9，页 2 返回 10—11。函数变量 num_pages 实际保存最后页索引，而不是“共有几页”；输出 page 0/2 表示第一页面对三页结果。无结果时函数单独输出 No results found。

对于链 k₀→k₁→k₂，先查 k₀，读取结果中的 k₁，再查 k₁。如果 k₂ 不再作为 key，就返回 k₂。终点可能仍作为前一条记录的 value 出现在搜索结果，所以不能用“搜索有结果”判断是否还要前进；需区分 key 与 value。

历史 archival_memory_search 声明 semantic search，真实 EmbeddingArchivalMemory.search 会计算 query embedding、调用 storage.query，然后对缓存候选分页。该类 top_k 默认 100：分页的是已检索出的候选集合，不等于逐页穷尽任意大数据库。如果正确文档不在候选内，仅翻页不能救回来；可以需要改查询。

本 demo 的 SQLite adapter 使用 case-insensitive literal substring 匹配，返回全部字符串候选，没有 embedding/HNSW/top_k 排名。它只验证分页接口和按结果动态生成下一条查询，不评价语义召回率。SQL 采用参数绑定，结果按插入顺序分页，便于明确把关键记录放在第二页。


### 6.1 历史后端的总量返回问题：本地demo没有覆盖的原行为【必须会】

锁定commit的 EmbeddingArchivalMemory.search 在候选缓存切片后，原代码是：

~~~python
results = self.cache[query_string][start:end]
results = [{"timestamp": get_local_time(), "content": node.text} for node in results]
return results, len(results)
~~~

这段返回“这一页有多少条”，而 base.py 的 archival_memory_search 把第二项当作完整total，计算last_page。新 [trace_contracts.py](复现/scripts/trace_contracts.py)直接提取并执行这段原方法体，提供12条预填充假Passage缓存，不调用embedding或向量库。count=5,start=0时返回5条、total=5，原工具显示page 0/0；手动请求page1仍能得到item5—9。静态阅读和隔离执行均证明这个commit有接口总量不一致，不能说官方分页一定可由页头自动穷尽候选。

本地SQLiteStore.query先COUNT(*)得到完整total=12，原工具在该adapter上显示page0/2，所以旧20/20证明的是**原工具体+替代后端的分页链**，不是历史EmbeddingArchivalMemory分页无误。本轮没有修改原commit或主demo来掩盖差异。缓存按query字符串保存，insert代码未清理旧query缓存；新插入后同query是否见到最新候选也有缓存边界，未运行完整后端来证明实时可见性。

分页公式适用条件是s>0、N>0、p是从0起的整数：start与last_page都是int，无Tensor shape。N=0时ceil(0/s)−1=−1，但代码走“No results found”分支，不展示该页号。page可传None或字符串'none'会归零、字符串'1'会转成1、'bad'会报ValueError；源码没有主动拒绝负页，不能把类型转换当作完备范围校验。s=5只是锁定常数，本地隔离符号namespace也显式提供同值。

## 7. 图 3 对应的历史源码路线

[图 3 原页](图片/page-3.png)没有 Tensor shape：主要对象是字符串、Message、工具参数字典、数据库记录和消息列表。底层 LLM 有权重，但记忆管理数据不是神经快权重。

| 路线 | 文件 / 对象 | 作用 |
|---|---|---|
| CLI 入口 | pyproject.toml → memgpt.main:app，cli/cli.py:run | 加载配置、Agent 与交互过程 |
| 事件循环 | main.py:run_agent_loop / process_agent_step | 处理用户事件、warning、heartbeat、失败恢复 |
| 模型调用 | Agent.step → _get_ai_reply | 拼消息与工具 schema，调用模型接口 |
| 调用执行 | Agent._handle_ai_response | 解析工具与参数，注入 self，调用函数 |
| 事实状态 | memory.py:CoreMemory | 字符串字段、长度限制、append/replace |
| 工具定义 | functions/function_sets/base.py | core、recall、archive 函数 |
| 系统消息刷新 | Agent.rebuild_memory | 将新事实渲染进 system message 并交换消息 |
| 历史持久化 | LocalStateManager.append_to_messages | 原消息插入 recall backend |
| 语义存储 | EmbeddingArchivalMemory.insert/search | chunk、embedding、数据库与分页 |
| 队列摘要 | Agent.summarize_messages_inplace | 原 LLM summarizer 与上下文裁剪 |
| 本地教学入口 | demo_memgpt.py:main | 原工具 + SQLite adapter + 确定性控制器 |

核心对象可按代码追踪：CoreMemory.human 是 str → core_memory_replace(self,name,old_content,new_content) 调用 edit_replace → 检查精确旧字符串与新长度 → 改 human → self.rebuild_memory() → 新事实成为下一轮主输入。

core_memory_append / replace 是模块函数，不是 CoreMemory 的方法；它们通过 self 访问 Agent 对象。self 在此显式绑定给函数。name 必须是 persona 或 human；replace 必须精确匹配旧内容，old_content 为空会报错，不能自动推断语义上“差不多”的事实。

conversation_search(self,query,page=0) 返回格式化字符串或 No results，底层 text_search 返回 results,total。archival_memory_insert 返回 None；archival_memory_search 返回包含时间戳和文本的字符串。返回 None 不等于失败，executor 的成功标志与返回数据必须区分。

重要的回调边界：demo 的工具函数与 CoreMemory 直接取自历史源文件，但 OfflineHost.rebuild_memory 是本地 callback，它只计数；OfflineHost.context 每次动态读取 repr(memory)，所以新事实仍进入本地上下文。没有冒充执行原 Agent.rebuild_memory 的完整 system message 更新实现。


### 7.1 原 Agent 的函数契约、返回项数与状态变化【建议会】

以下来自固定历史源码的静态阅读，未执行完整模型runtime。Agent的self是实例；process_agent_step是run_agent_loop内部函数，不是Agent方法。类型注解是说明，不自动保证返回结构与实测一致。

| 对象 | 全部参数/默认 | 实际返回、状态、位置 |
|---|---|---|
| Agent._get_ai_reply | message_sequence：list[dict]，无默认；function_call='auto'字符串；first_message=False布尔 | ChatCompletionResponse；模型/API调用，检验finish_reason。由step调用，可能抛context/响应错误 |
| Agent._handle_ai_response | response_message：响应Message，无默认；override_tool_call_id=True | (list[Message],heartbeat_request bool/None,function_failed bool)。解析JSON/执行工具，可改core/存储，可能修改response_message的tool_calls/id；由step调用 |
| Agent.step | user_message：str/None无默认（通常JSON文本）；first_message=False；first_message_retry_limit=FIRST_MESSAGE_ATTEMPTS=10；skip_verify=False | 实际5元组：(list[dict],heartbeat_request,function_failed,active_memory_warning,completion_tokens int)。追加消息、持久化、设warning标志；overflow时摘要并递归重试 |
| Agent.summarize_messages_inplace | cutoff=None；preserve_last_N_messages=True；disallow_tool_as_first=True | None；调用模型摘要、裁剪/插入消息、复位warning。cutoff参数在函数体被重新设为0并计算，不能认为传入cutoff直接控制裁剪。默认保护末3条消息 |
| Agent.rebuild_memory | 只有self | None；重新构建system message并交换当前第0条，受tool成功编辑触发；不是模型权重更新 |
| process_agent_step | user_message、no_verify均无默认 | (new_messages,user_message,skip_next_user_input)；调用step解包5项，按warning→failure→heartbeat优先级生成后续事件 |
| run_agent_loop | memgpt_agent、config、first、ms无默认；no_verify=False、cfg=None、strip_ui=False | CLI交互循环，操作输入与Agent；未当作无交互测试运行 |
| EmbeddingArchivalMemory.insert | memory_string无默认，应为str | 正常True并写Passage；非str分支返回TypeError对象而非raise；未执行完整embedding路径 |
| EmbeddingArchivalMemory.search | query_string无默认，应为str；count=None；start=None | 当前页dict列表和当前页长度；更新query缓存，读取后端；非str可返回TypeError对象。默认count取top_k=100、start取0；0值也被truthiness当默认处理 |

step的返回注解写Tuple[List[dict],bool,bool,bool]四项，实际return五项；新AST核对记录5，main实际也按五项解包。因此不能只抄注解给调用者四项。_handle_ai_response对超过一个tool call只使用第一项；旧function_call字段会raise DeprecationWarning；它不是本commit的任意多工具并行调度器。request_heartbeat从args弹出，非bool/None被降为False，再绑定self。错误返回的failure=True让外层安排恢复事件。

原文图3从主上下文左到右流入Output Buffer，再由executor处理完成tokens。绿色双向箭头为archive读写；橙色箭头是工具修改working context；蓝色箭头是queue写recall与工具读回；粉色/蓝色上箭头表示摘要/队列重入主输入。图里的数据库圆柱不是参数Tensor；执行器/队列管理器也没有通过backprop学习权重。模型推理生成token，记忆内容是字符串/Message列表，训练阶段不在该图流程中新增梯度算法。完整模型的Embedding/attention/RoPE/LM head等由底层模型提供，本地不执行其tokenizer、KV cache、解码或量化。

走一条事实：用户事件“City: Beijing”→queue/recall→LLM生成core编辑参数→executor→CoreMemory.human→rebuild_memory重建system→下一次模型输入含新事实。后来用户说Hangzhou时，replace修改原精确文本，再重复上述路线。保存数据库不等于同时把整库都放入模型窗口；每条绿色/蓝色读回箭头均要占用主输入预算。矩形框各自对应§7表中的类/函数，底层模型参数仅在LLM方框，未在工具demo中加载。

## 8. 原论文实验与结论边界

表 1 收集的是 2024-01 时点模型窗口；它不是当前模型规格表。阅读时只用它理解当时问题，不据此推荐今天购买或部署的模型。

表 2 DMR（[第 5 页](图片/page-5.png)）使用 Multi-Session Chat 前五次对话，另外生成第六次 session 的特定问答。准确率由 LLM judge 判定，同时报告 ROUGE-L recall，均越高越好。GPT-4 从 32.1% 到加 MemGPT 的 92.5%，提高 60.4 个百分点；ROUGE-L(R) 从 0.296 到 0.814，提高 0.518。GPT-4 Turbo 35.3%→93.4%，提高 58.1 个百分点；GPT-3.5 Turbo 38.7%→66.9%，提升较小。

这些比较是同底层模型的不同记忆系统：baseline 看过去五轮的有损摘要，MemGPT 能查询完整历史。多次模型/检索调用和存储条件并未被约束为完全相同成本，因此不能将提升只归因于某一个模块，或当成同预算推理比较。

表 3 opener 使用与 persona 和人类 opener 的相似性指标，不是用户点击/留存或真人偏好。GPT-4 MemGPT SIM-1=0.868，高于 Human=0.800，但 SIM-H=0.773，而人类对自身参考为 1.000。较高 persona similarity 不等于普遍比真人更会聊天；更长、包含更多 persona 信息的回答也影响指标。

### 8.1 指标公式和原图能支持的范围【建议会】

DMR是给出过去多session才能回答的问题，accuracy由LLM judge按prompt判定“记忆答案是否正确”，不是自动字符串匹配；ROUGE-L recall是基于最长公共子序列的参考覆盖率。为解释量纲可写 $R_L=\operatorname{LCS}(\hat y,y)/|y|$，y为参考token序列、hat y为预测，长度与LCS均为int，结果float；精确分词/实现需实验代码确认，不据此宣称重跑原评分。参考[a,b,c]、预测[a,x,c]的LCS长2，recall=2/3，即使额外输出很多无关内容也未在此项被充分惩罚。故它不是事实无幻觉保证。

GPT-3.5的38.7%→66.9%提升28.2个百分点，GPT-4的32.1%→92.5%提升60.4个百分点，相对后者baseline约188.16%增长；“百分点”与“相对百分比”不能混读。置信区间、同调用预算和judge一致性统计不在原表中充分给出，不补造显著性结论。表1是历史上下文窗口快照，不在本篇评估当前产品规格。

原文称opener分数为CSIM，表中SIM-1/3与persona标签比较、SIM-H与人类opener参考比较；SIM-1/3的精确聚合细节和embedding配置在这些原页未展开，不自行补造。不能把SIM-H=1的human自参考当成同等独立生成评价。下式解释向量检索常用cosine，未认定等于已核查的opener评分实现： $\cos(u,v)=u^\top v/(\|u\|_2\|v\|_2)$ 中u/v为长度d_e的浮点embedding，内积/范数给标量，需非零向量；本地demo无embedding，官方评价实现未在本地运行。解释例u=[1,0],v=[1,1]得1/sqrt(2)≈.7071，说明相似不是二元正确判定。GPT-4 MemGPT的SIM-1 .868比human .800高.068，同时SIM-H .773低于human自参考1达.227；仅可支持该参考相似度下的结果，不是实际用户更喜欢的证据。

图5横轴是Documents Retrieved数量K，不是模型token窗口或数据库总容量；纵轴accuracy。K增加会让固定上下文reader截断文档，MemGPT则按需查询/翻页，调用数可能不同。原图5/7/8没有逐点机器可读数据时，只讨论原文明确的数量设置与曲线排序，不目测生成精确小数。图6示例的页号/每页数量展示任务流程，也不能把其“10 results”当作本commit的默认5。图1/2/4的事实编辑与历史查找是单段轨迹，不是额外的总体准确率实验；对应工具分别是core编辑、recall搜索/重入上下文，其数据是消息字符串而非网络参数。

## 9. 本地 demo：哪些是真代码，哪些是替代

[实验代码](复现/scripts/demo_memgpt.py)的 load_original_symbols 用 Python ast 从固定文件提取 CoreMemory 类与五个工具函数。AST 是 Python 源码的语法树；compile/exec 执行选出的原函数体，跳过依赖完整 runtime 的顶层 imports。类/函数体未改写，Optional、math、json 和原版分页常数由 namespace 提供。

class 定义有状态对象，__init__ 构造对象；CoreMemory 的 @classmethod load 是从字典恢复字段的类方法。原 load 没有恢复 char limit，因此本地 restore 显式重新构造并带上 100/200 的限制，不能假定只恢复字符串就恢复了所有约束。

| 对象 | 参数与结果 | 状态/范围 |
|---|---|---|
| load_original_symbols() | 返回原符号字典和文件散列 | 不导入完整历史包 |
| SQLiteStore.query(kind,query,count,start) | 返回 rows,total | recall/archive 共用表，以 kind 分区；不是语义搜索 |
| OfflineHost.call(name,args,request_heartbeat=True) | 返回 result,success | 原工具执行，结果作为 atomic block 入队；本地控制器 |
| OfflineHost.append(block,role='tool') | 无返回值 | 保存 recall、统计压力、按字符预算换出 |
| OfflineHost.context() | 返回字符串 | 规则+core+摘要+队列；每次动态生成 |
| solve(host,start,paginate=True,max_calls=100) | 返回 answer,calls,steps | 从真实工具结果提取下一 UUID；不读取 gold |
| save/restore | JSON 状态 | 保存 core、队列、摘要；数据库单独存 SQLite |
| main() | JSON、SQLite、状态文件 | 建数据、对照、关闭/重开核验 |

主要数据流：原函数定义 → host 将 tools 所需 self 属性接到 SQLite adapter → 脚本发事件或调用参数 → 原工具读写 → result 字符串返回 → queue append → 换出检查 → 下一轮从分页结果决定查询或终止。

工具执行没有被替换成预设答案。控制策略却是已知的确定性算法，知道如何识别 Key/Value 格式并翻页；不能由其成功率推断 LLM 能自主学会同样策略。SQLiteStore、queue manager、summary、heartbeat dispatch 都是本地教学实现。


### 9.1 原 CoreMemory 和五个工具的完整契约【必须会】

[contracts_trace.json](复现/outputs/contracts_trace.json)记录33个实际可导入对象签名：原CoreMemory 9项、工具5项、本地adapter/controller及入口19项。每个来源文件哈希与固定commit校验；CoreMemory的普通方法self隐式绑定，base.py的工具却是模块函数，需要executor显式传self，两者调用约定不同。

| CoreMemory对象 | 全部参数/默认和类型 | 返回/状态、调用关系 |
|---|---|---|
| __init__ | persona=None、human=None（正确编辑时应str）；persona_char_limit=None、human_char_limit=None（int/None）；archival_memory_exists=True（bool） | None；设置字段。若persona/human保持None，append的字符串拼接会失败；本demo传初始字符串 |

| to_dict | 只有self | dict含persona/human两str，不含limit；save调用 |
| load，classmethod | state无默认，dict含persona/human；cls隐式传入 | 新CoreMemory，用默认None limits；恢复内容并不恢复容量约束 |

| edit | field/content无默认，均str | 长度int；按field分派上两方法，非法field为KeyError |
| edit_append | field/content无默认str；sep='\n'字符串 | 长度int；旧字段+sep+content后走限长检查；空字段也会先加换行 |

persona_char_limit/human_char_limit的判定使用if limit，因此0和None都不启用限制。new字符串的len按Python字符计数，不是UTF-8字节也不是模型token。实验新检查将'human=abc abc'替换'abc'→'x'后得到'x x'，返回3；空old/missing/非法field以及超长写入均记录实际错误并核对旧状态未改。原CoreMemory.load后limit=None，21字符可写；本地custom restore重新指定200/100，才恢复这两个约束。

| 原工具（模块函数） | 全部参数/默认 | 返回、副作用、链路 |
|---|---|---|

每个函数的None是合法成功返回，不是“没有执行”。工具抛异常才由executor包装为失败；host返回tuple(result,success)，成功标志和返回值分开。新检查core append结果None、success=True、next_event='yield'；非法page结果为错误str、success=False，即使request_heartbeat=False也设置heartbeat。这是本地兼容控制器的实际行为，不表示完整Agent parser已运行。

### 9.3 原代码块、API及连续数据路线【必须会】

原工具编辑代码：

~~~python
new_len = self.memory.edit_replace(name, old_content, new_content)
self.rebuild_memory()
return None
~~~

一句话：先成功改事实，再刷新下一轮可见记忆。它位于executor→工具→CoreMemory路径；new_len是int，但工具最终不返回它。edit_replace内部先检查old非空和精确存在，再str.replace得到新字符串，edit_human/persona先验长度后才赋值。失败抛异常则后两行不执行。数值例'abc abc'→'x x'长度7→3；old不存在时长度和内容都不变。掌握这段不需要torch/backprop。

原工具分页代码：

~~~python
results, total = self.persistence_manager.archival_memory.search(query, count=count, start=page * count)
num_pages = math.ceil(total / count) - 1
results_formatted = [f"timestamp: {d['timestamp']}, memory: {d['content']}" for d in results]
~~~

一句话：把后端页记录和总量包装成模型能读的文本。tuple解包区分rows和total；math.ceil向上取整；列表推导式将每条dict转成str；f-string插入字段；json.dumps再将list[str]序列化，返回整个字符串，未直接返回JSON对象。这段依赖total正确性，历史后端错误已实测，替代adapter给完整N。空结果分支返回No results字符串。

本地执行/回填原代码：

~~~python
try: result=self.symbols[name](self,**args);success=True
except Exception as e: result=str(e);success=False
self.trace.append(block);self.append(block)
return result,success
~~~

一句话：调工具并把成功或错误回填上下文。symbols[name]从注册字典取函数；**args把dict键展开为命名参数，self是显式首参数。try/except捕获工具异常，不保证外部数据库事务回滚。trace.append记录调用，host.append先写recall后检查queue预算；这个顺序是持久化动作，不是“模型说自己记住了”。request_heartbeat生成next_event标记，真正的下一轮在solve的循环里推进，没有LLM调度。

| 变量 | 来源/用途 | type及数据布局 | 下游 |
|---|---|---|---|
| namespace/symbols | AST提取出的原对象 | dict[str,class/function] | host调用与CoreMemory构造 |
| memory.persona/human | core字符串 | str，受字符上限 | repr→context |
| args | 工具参数 | dict，query/page或name/content等 | **args调用 |
| SQLite rows | query结果 | list[3元tuple]；再变list[dict] | 原工具分页 |
| results/total/page/count | 页记录、完整数量、页号、页大小 | list[dict]/int/int/int | 前缀+格式化str |
| result | 工具反馈 | str或None，错误也是str | success与block |
| block | 调用+参数+反馈原子块 | dict，包含name/args/result/success等 | queue与recall |
| queue | 当前块列表 | list[dict]，可变长度 | JSON→当前context |
| context | 当前主输入替代 | str，最多1200字符 | 本地可见性检查，未tokenize |
| current/seen/steps | solve游标、防环、查询轨迹 | UUID str/set[str]/list[dict] | 下一查询或终点 |

实际路线：Path找到原repo→ast.parse源码→筛出ClassDef/FunctionDef→compile成代码对象→exec放入提供Optional/math/json/常数的namespace→构造host→传字符串参数→数据库rows→工具格式化str→atomic block→主context→result_rows解析→regex取得下一UUID。AST不是改函数体的工具；本轮保留原节点并跳过需要完整runtime的imports。__file__/resolve/parents确定路径，不依赖碰巧的cwd。SimpleNamespace为manager提供recall_memory/archival_memory两个属性。

CoreMemory继承object，非Tensor模块；@classmethod使load收到cls而不是已有实例self。类实例属性存字符串；字典推导/列表推导只组织对象，不隐含训练；with TemporaryDirectory用于本轮隔离probe，退出删除仅临时probe文件，已交付数据库未动。SQLite '?'参数绑定把数据与SQL语句分开，count/start用于LIMIT/OFFSET；lower/instr是literal substring，不能算embedding近邻搜索。json.ensure_ascii=False保留Unicode文本，不使字符计数等于token数。所有类型/shape映射属于系统数据，不假装底层LLM的Tensor已测量。

## 10. 已运行实验

核心事实 City: Beijing 经原 replace 工具变为 City: Hangzhou。超过 human=200 字符上限的写入报错，旧值保持不变；随后脚本将长内容写入 archive，完成显式错误恢复。两个成功 core 编辑触发 callback 两次。

一条 Aster 项目的 secret code 先进入历史，经过 40 条填充消息后已经不在当前上下文。conversation_search 从 recall 找回记录，返回结果再次进入上下文。基准查询并没有预先把 secret code 填到 core 或摘要里。

多跳测试：depth_links=1、2、3、4，各 5 次，总 20 次。随机 UUID 来自固定种子 2026；每条真正 Key/Value 前插入 7 条只提及 key 的干扰记录，因此真正 key 在第 1 页（0-based）的候选中。上传后再加入噪声，把初始记录移出当前窗口。

| 工具流程 | 20 个合成任务 exact-answer rate |
|---|---:|
| 只看第一页 | 0/20 |
| 只允许一次工具调用 | 0/20 |
